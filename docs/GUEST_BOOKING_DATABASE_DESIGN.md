# OBNAR VACANCES — Guest Booking Database Design

**Status:** design only — NOT a migration and NOT applied  
**Branch:** `pwa-foundation`  
**Environment inspected:** staging project `rhxeclddohpwtpzkruzm` (read-only)  
**Date:** 22 November 2026

## 1. Scope and safety boundary

This design enables guest booking without changing the existing registered-traveler experience. It does not authorize anonymous table access, weaken RLS, change Storage policies, deploy Edge Functions, or modify staging/production.

The implementation must be delivered as one reviewed database migration after the dependent views, functions, triggers, grants, and frontend reads are mapped. The migration filename must be generated by the Supabase CLI; this document is not executable SQL.

## 2. Verified staging facts

- `bookings.traveler_id` is NOT NULL and references `profiles(id)`.
- `bookings` stores date range, guest count, total, payment state, deposit, payment due time, per-night price components, and test flag.
- Active booking statuses are `pending`, `awaiting_admin_approval`, `awaiting_payment`, and `confirmed`; active overlap protection exists through GiST exclusion constraints. `create_booking()` also takes a property-scoped advisory transaction lock and independently checks overlaps.
- `bookings_confirmed_requires_verified_payment` and the `enforce_booking_confirmation_payment()` trigger protect confirmation/payment consistency.
- `booking_cancellations.requester_id` is NOT NULL, references `auth.users(id)`, and requester role allows only `traveler` and `owner`.
- `booking_cancellations_booking_id_key` is UNIQUE. The first guest release retains one cancellation lifecycle per booking; a rejected request does not permit creating a second cancellation row.
- `booking_cancellation_history.actor_id` is nullable; actor role allows `traveler`, `owner`, `admin`, and `system`.
- `notifications.user_id` is NOT NULL. `notify_new_booking()` unconditionally inserts a traveler notification using `NEW.traveler_id`; this must be guarded for guests. Owner and main-admin notifications must remain.
- Existing registered-user RPCs include `create_booking()`, `request_booking_cancellation()`, and `submit_payment_receipt()`. They are SECURITY DEFINER and must remain restricted to their existing authenticated flows.
- `notify_booking_cancellation()` derives recipients from booking identity and requester role; it must be reviewed for a guest requester so it never attempts to notify a NULL guest user.
- `properties` has required `owner_id`, `price_per_night`, `capacity`, and `status` fields used by the current booking logic.

## 3. Proposed data model

### 3.1 Booking identity

Keep the existing `traveler_id` foreign key, but allow NULL for guest bookings. Add:

- `guest_name` — nullable text, bounded length, trimmed and validated server-side.
- `guest_phone` — nullable normalized phone string; private personal data.
- `booking_reference` — nullable unique opaque public reference; not an authenticator.
- `guest_access_secret_hash` — nullable fixed-length SHA-256 digest (hex or bytea; choose one representation consistently).
- `guest_access_expires_at` — nullable timestamptz.
- `guest_access_revoked_at` — nullable timestamptz.

Add a CHECK enforcing exactly one identity mode:

- Registered: `traveler_id IS NOT NULL`, and all guest identity/credential fields are NULL.
- Guest: `traveler_id IS NULL`, guest name/phone/reference/hash/expiry are present, and revocation is either NULL or a timestamp.

Do not use `booking_reference` as a password. Generate it independently from the 256-bit access secret. Store only the secret hash. The plaintext secret is returned once by the create endpoint.

Before adding the CHECK, verify every existing and test row against the registered identity branch. The FK remains intact for registered users.

### 3.2 Cancellation ownership

- Change `requester_id` to nullable while preserving its FK to `auth.users(id)`.
- Extend requester role with `guest`.
- Add a CHECK linking identity to role: guest requester means NULL requester_id and a guest booking; traveler/owner requester means a non-NULL requester_id and existing authorization checks.
- Keep `reviewed_by` unchanged and nullable.
- Keep the unique `booking_id` constraint for the first release. A rejected request is terminal for this booking's cancellation lifecycle; do not silently delete/recreate the request or overwrite history. Any later re-request feature needs a separate explicit policy and schema decision.
- Add `guest` to cancellation-history actor roles. Guest history entries use NULL actor_id and must not contain guest phone, secret, or raw credential material.

The server-side guest cancellation routine must bind the request to a booking only after reference + secret verification, and must re-check booking state inside the transaction.

### 3.3 Notifications

Update `notify_new_booking()` so that:
- Traveler notification is inserted only when `NEW.traveler_id IS NOT NULL`.
- Owner notification continues for both registered and guest bookings.
- Main-admin notification behavior remains unchanged.
- No guest notification row is created because `notifications.user_id` cannot be NULL.

Review `notify_booking_cancellation()` separately:
- For guest requests, notify the owner and main admin as required by the existing state machine.
- Never include a NULL guest user as a recipient.
- Keep the notification trigger transactional; avoid notification failure breaking a valid guest cancellation unless the current system intentionally treats notification as mandatory. The final behavior must be explicit and tested.

### 3.4 Payment receipt

Do not relax `submit_payment_receipt()` or existing Storage policies.

Guest receipt flow:
1. Edge Function validates reference + secret and rate limits.
2. Edge Function validates file size (5 MiB), allowlisted format, and file signature.
3. Edge Function uploads to the existing private `payment-receipts` bucket under a server-generated path, never a browser-selected path.
4. A private database routine attaches the uploaded object path to the already-authorized guest booking after rechecking payment state.
5. Existing owner/admin signed-URL access remains the only read path.

The exact server-only database role and Storage credential pattern must be verified against project settings before implementation. No service credential may enter browser code.

## 4. Private database routine boundary

Guest-only routines should live in a non-exposed schema (for example, a dedicated internal schema) rather than exposed `public`. Confirm schema exposure and grants before choosing the final schema.

Required operations:

- Create guest booking: validate approved property, dates, capacity, guest fields, current price and commission; lock the property; reject overlap; insert booking and credential metadata atomically.
- Authorize guest access: validate reference/hash/expiry/revocation and apply throttling. Return only an authorization result, not a full booking row.
- Read guest status: return a minimal guest-safe projection after authorization.
- Request guest cancellation: apply the existing five-day and exceptional-cancellation state machine, preserving the active booking and blocked dates while review is pending.
- Attach receipt: bind a validated server-uploaded path to the authorized booking.
- Rate limit: atomically throttle by keyed digest of normalized reference/contact/request context. Do not trust caller-supplied IP headers.

Every privileged routine requires fixed `search_path`, strict input validation, explicit EXECUTE grants, and a deliberate SECURITY INVOKER/DEFINER decision. Do not grant EXECUTE to PUBLIC, anon, or authenticated by default. If an Edge Function calls a private routine through PostgREST, confirm that the chosen schema is not exposed; otherwise use a narrowly scoped server-side database connection/role. Never solve this by exposing a broadly privileged SECURITY DEFINER function.

## 5. Existing behavior that must remain unchanged

- Registered `create_booking()` continues to require `auth.uid()`.
- Registered traveler cancellation continues to use the current authenticated routine and permission checks.
- Registered receipt uploads retain the current user-specific Storage path and `submit_payment_receipt()`.
- Booking overlap exclusion constraints and property advisory lock remain.
- Confirmation still requires verified payment.
- Existing owner/admin views and signed receipt access remain restricted.
- No guest contact data is exposed in public property views, traveler queries, or owner exports in the first release.
- Owner and main-admin screens may display guest name/phone only after their existing property/admin authorization has been verified.

## 6. Cancellation policy mapping

- Cancellation at least five days before check-in: full deposit refund eligibility according to the agreed policy.
- Less than five days: exceptional review; owner response deadline is 48 hours; a refusal can be escalated to main admin.
- Material property mismatch on arrival is urgent and bypasses ordinary owner waiting.
- Owner silence after 48 hours moves the request to admin review; silence is neither approval nor rejection.
- Owner approval of an exceptional cancellation does not automatically grant a full refund. Main admin makes the refund decision.
- While a request is pending, booking status remains active and dates stay blocked. Release dates only after the final approved cancellation transition.
- Owner-initiated cancellation retains its separate agreed refund treatment.

The guest routine must reuse the same state machine semantics, not create a parallel simplified cancellation process.

### 11.3 RLS on booking-related tables

Read-only policy inspection found:

- `bookings`: participant SELECT policy for authenticated users (main admin, traveler, or property owner) and main-admin UPDATE policy. No direct anon policy was observed.
- `booking_cancellations`: authenticated SELECT policy for main admin, requester, traveler, or property owner. No direct anon policy was observed.
- `booking_cancellation_history`: authenticated SELECT policy for main admin, traveler, or property owner. No direct anon policy was observed.

RLS is enabled on these tables in the inspected project. Guest access must not be implemented by adding an anon SELECT/INSERT/UPDATE/DELETE policy. Guest operations remain server-mediated and use narrowly scoped routines.

**Important follow-up:** participant policies currently depend on `traveler_id = auth.uid()`; when traveler_id becomes nullable, guest identity must not accidentally match registered-user predicates. Owner/admin visibility of guest contact fields requires a separate authorized projection and must not expose guest columns through broad participant reads.

These policies are registered-user specific and must remain unchanged for the guest feature. Guest receipt upload must use a server-only controlled upload/attachment route; do not add anon Storage policies or relax the current path ownership rule.

### 11.7 Function-body and effective-grant review — read-only staging audit

The following function behavior was confirmed from `pg_get_functiondef` and effective EXECUTE ACL inspection:

- `create_booking(uuid,date,date,integer)` is SECURITY DEFINER with a fixed search path. It explicitly rejects a NULL `auth.uid()`, writes that UID into `traveler_id`, and is executable by `authenticated` and `service_role` (not anon/PUBLIC). Keep it as the registered-user route; do not weaken its authentication guard.
- `request_booking_cancellation(uuid,text,text)` is SECURITY DEFINER and requires `auth.uid()`. It authorizes traveler/owner by booking/property ownership, inserts `requester_id = auth.uid()`, and applies the current cancellation state machine. It is executable by `authenticated` (and owner/postgres context), not anon. Guest cancellation must be a separate server-authorized route and must preserve this routine unchanged.
- `submit_payment_receipt(uuid,text)` is SECURITY DEFINER and requires `auth.uid()`; it updates only a booking owned by that UID and requires the Storage path's first segment to equal that UID and second segment to equal the booking ID. It is executable by `authenticated` and `service_role`, not anon/PUBLIC. Do not reuse it for guest receipts or relax its path checks.
- `notify_new_booking()` is a trigger function (not directly executable by anon/authenticated) that currently inserts a traveler notification unconditionally using `NEW.traveler_id`. A NULL traveler would violate `notifications.user_id NOT NULL`. Its guest-safe revision must skip only the traveler notification while retaining owner notification.
- `notify_booking_cancellation()` is a trigger function (not directly executable by anon/authenticated). Its current recipient selection handles traveler requester, owner requester, and main admin; it does not include a guest requester branch. A guest request would not notify the owner under the current CASE/UNION logic. Add a deliberate guest branch for owner/admin recipients and never attempt a guest notification.
- `respond_to_booking(uuid,text)` is SECURITY DEFINER, requires authentication, and checks property ownership before changing a pending booking. On rejection it inserts a notification addressed to `v_traveler_id` without a NULL guard. This is another registered-only path that needs a safe guest-aware notification branch if owners can reject guest bookings.
- `admin_review_booking_cancellation(uuid,text,text,text)` verifies the main admin and sends notifications only to non-NULL booking traveler/owner IDs. This recipient filter is NULL-safe for a guest booking, but guest-facing status communication must remain via the secure guest-status endpoint, not notifications.
- `sync_property_public_booking_dates()` is SECURITY DEFINER with a fixed search path and maintains only `property_public_booking_dates` rows for approved properties and qualifying paid/verified bookings. It does not depend on `traveler_id`; preserve its current eligibility criteria and test both insert/update/delete behavior.
- The payment-confirmation guard and the remaining admin/expiration/refund functions still require complete semantic review before migration; do not infer their safety from the dependency list alone.

Effective EXECUTE ACLs inspected for the key RPCs do not show anon or PUBLIC grants. Trigger functions are postgres-only. This supports retaining registered RPC boundaries rather than granting anonymous execution.

### 11.8 Public availability-date projection

The indirect relation is now characterized:

- `property_public_booking_dates` is a table with RLS enabled and a SELECT policy for `anon` and `authenticated` using `true`; its exposed fields are the safe availability tuple `property_id, check_in, check_out`.
- `property_public_booked_dates` is a public view owned by postgres that selects only those same three fields from the table. The view has an anon SELECT grant. It does not expose traveler identity, guest contact details, payment receipt paths, or booking IDs.
- This is an intentional public availability projection, not permission to expose `bookings` or cancellation tables. Keep the projection limited to property/date fields; do not add guest fields or broaden it to full booking rows.
- `sync_property_public_booking_dates()` deletes obsolete date tuples only when no other qualifying booking remains, and inserts qualifying tuples with conflict avoidance. Its current predicate requires approved property, non-test booking, confirmed/completed status, verified payment, positive deposit, non-empty receipt path, and payment verification timestamp.
- Schema USAGE privileges exist for anon and authenticated on `public` and `graphql_public`. A direct read of the PostgREST schema setting through the database session returned NULL, so the actual Data API exposed-schema configuration remains unconfirmed and must be checked in project settings before choosing the private guest-routine schema.

### 11.9 Newly confirmed guest compatibility blockers

1. Guest booking insert cannot call the current `create_booking()`; its auth requirement and non-null traveler assignment are deliberate.
2. Guest cancellation cannot call `request_booking_cancellation()`; requester identity is bound to `auth.uid()` and `requester_id` is populated from it.
3. Guest payment cannot call `submit_payment_receipt()`; it requires a registered traveler UID and UID-prefixed object path.
4. Owner rejection of a guest booking can currently fail at the notification insert because `respond_to_booking()` assumes `traveler_id` is non-NULL.
5. Guest cancellation notifications need an explicit owner/admin recipient branch in `notify_booking_cancellation()`.
6. The public availability projection is the only confirmed anon-readable booking-related surface in this inspection; core booking/cancellation tables remain protected by authenticated participant policies.

These are design findings only. No SQL, policy, trigger, function, Storage, or data changes were applied.


### 11.10 Additional trigger, row-state, and RLS checks

- `enforce_booking_confirmation_payment()` is a SECURITY INVOKER trigger function (not SECURITY DEFINER). When a booking becomes `confirmed`, it requires verified payment, a positive deposit, a non-empty receipt path, and a verification timestamp. It locks the property row and rejects overlapping confirmed date ranges. It does not read `traveler_id`; preserve this guard for guest bookings as well.
- `expire_unpaid_bookings()` is SECURITY DEFINER and expires only overdue `awaiting_payment` bookings with unpaid/rejected payment and no pending cancellation request. Its notification recipient query filters NULL user IDs, so it is already NULL-safe for a guest booking. Keep this behavior and test guest expiry without generating a guest notification.
- The inspected staging snapshot currently contains **0 booking rows**, **0 cancellation rows**, and **0 cancellation-history rows**; `notifications` contains 32 rows. The booking status/payment-state aggregate is empty. Therefore, there are no existing staging booking fixtures to validate against the proposed identity CHECK. This is a staging snapshot observation, not a statement about production.
- Additional RLS policies inspected:
  - `properties`: anon can SELECT approved properties only; authenticated users can read approved properties, their own properties, or all properties as main admin. Owner INSERT requires owner role and approved owner verification; owner UPDATE is limited to allowed statuses; admin DELETE is restricted to main admin.
  - `profiles`: authenticated users can read their own profile or main-admin-visible profiles; self INSERT is restricted to traveler role; UPDATE is self/admin only.
  - The participant policies on bookings/cancellations/history remain authenticated-only and continue to depend on traveler/owner/admin relationships. Do not add guest access through these table policies.
- No PII or row-level booking details were selected during the row-count check.

The remaining inspection is focused on the full bodies of the other admin/refund/cancel functions and the actual frontend query/export surface, plus confirming the Data API exposed-schema setting in the dashboard. The current audit is still insufficient to generate a migration.


### 11.11 Remaining RPC and frontend dependency findings

#### Admin and owner RPCs

- `admin_review_owner_booking(uuid,text,text)` is SECURITY DEFINER, checks the main-admin identity, locks/reads the booking and applies the owner-booking approval/rejection state transitions. Its notification branches insert directly to `v_booking.traveler_id` without a NULL guard. A guest booking can therefore fail the transaction when an admin approves/rejects the owner's decision unless the notification branch is made guest-safe.
- `admin_review_payment_receipt(uuid,text,text)` is SECURITY DEFINER and main-admin-only. It reads/updates the booking then inserts traveler and owner notifications using `v_traveler_id`; the traveler notification is not guarded for NULL. A guest payment review cannot use this routine as-is; a NULL notification recipient can abort the transaction. Guest receipt verification needs a separate server-authorized route or a carefully reviewed guest-aware branch, while retaining the registered path.
- `admin_review_refund_execution(uuid,text,text)` is SECURITY DEFINER and main-admin-only. It verifies the refund proof object and records execution/history; its notification recipient query filters NULL IDs. This part is NULL-safe for guest identity, but its eligibility and history workflow still requires regression tests for guest cancellation rows.
- `admin_review_booking_cancellation(uuid,text,text,text)` is main-admin-only and filters NULL traveler/owner notification recipients. It can avoid inserting a guest notification, but guest status must be obtained through the guest secret flow.
- `cancel_booking_by_traveler(uuid)` explicitly requires `auth.uid()` and matches `traveler_id = auth.uid()`; it is registered-traveler-only. Do not reuse it for guest cancellation.
- `admin_review_owner_booking`, `admin_review_payment_receipt`, `respond_to_booking`, and both notification triggers must be treated as explicit guest compatibility work items, not assumed safe merely because they are SECURITY DEFINER.

#### Frontend query and export surface (branch `pwa-foundation`, `index.html`)

- Registered booking creation calls `create_booking()`; the current page flow does not yet implement guest booking.
- Traveler dashboard queries bookings with `traveler_id = currentUser.id` and reads cancellation requests for those booking IDs. This remains registered-user-only and must not become a guest access path.
- Admin booking loader selects `traveler_id`, then fetches profiles only for non-null traveler IDs. Its rendering currently resolves traveler details through the profile map and falls back to “unknown traveler”; it does not yet render `guest_name`/`guest_phone`. A future admin guest display needs a separately authorized projection and must avoid trying to resolve a guest through `profiles`.
- Owner booking loader scopes bookings by the owner's property IDs and currently selects no traveler ID, profile, guest name, or guest phone. It must be extended to show guest contact details only after owner authorization is established, without broadening public or traveler queries.
- Owner export fetches only property/date/guest-count/price/status/payment fields and contains no traveler or guest name/phone columns. Preserve this first-release policy: do not add guest contact information to owner exports.
- Main-admin export currently includes registered traveler name and phone from the profiles map. Guest identity fields are not present in the export yet. The approved design decision is not to include guest name/phone in owner exports; main-admin export policy should remain explicit and least-privilege when guest columns are added.
- Admin cancellation queue reads cancellation fields and booking IDs but does not fetch/display guest contact data. Guest requests need a secure, admin-authorized display path; do not expose guest credentials or secret hashes.
- Owner and admin receipt viewing uses signed URLs for the private bucket. Keep this pattern; never make the bucket public.

#### Configuration limitation

The SQL session confirms `USAGE` grants on `public` and `graphql_public`, but it does not reveal the dashboard's actual PostgREST exposed-schema configuration. The configuration was not verifiable through the inspected SQL setting. The final private schema choice is blocked until the project's Data API > Exposed schemas setting is checked directly.
